## 0. 测试报告校准（必须先读）

两份报告整体专业度高，但存在 6 类系统性误差，不能照单全收。

### 0.1 「Skill 工具只加载 SKILL.md 不执行代码」—— 架构认知偏差（两份报告均提及）

测试5 SYS-01 / 测试6 P0-01 均把「3 个 agent 跨技能调用需手动模拟」标为 P0 架构限制。

**真相**：
- quick-knowledge 是**指令式技能体系**（SKILLS_SPEC §3），所有「调用 agent」本质是 Claude 在主对话中读 agent 的 SKILL.md 指令并按其执行，**不是 RPC 调用**。
- Skill 工具加载目标 SKILL.md 是设计预期，不是 bug。「不可执行代码」是 Claude Code harness 的固有约束，非 quick-knowledge 可控。
- 测试中「需手动模拟」的实际含义：测试者用 Skill 工具加载 agent SKILL 后未继续在主对话中按指令执行，是**测试执行偏差**，非 spec 缺陷。

**处置**：删除「实现 Agent 可执行封装」类建议（测试5 P0-01、测试6 P0-01）。但衍生真问题保留——**部分被调用方 SKILL 的「被调用契约」未明确**（如 research-agent 未声明「ingest 调用我时应返回什么结构」），见 WP1。

### 0.2 「归档 wikilink 后缀破坏 Obsidian 解析」—— v1.6.0 已修复

测试5 P0-10 称归档后 `[[X (已归档)]]` 破坏 Obsidian 文件名匹配。

**真相**：v1.6.0（commit `618897b`）的 WP9 已落地 wikilink 命名约定（`references/wikilink-conventions.md`），规定归档链接必须用别名语法 `[[target|target (已归档)]]`。archive SKILL §6 已遵守。

**处置**：P0-10 删除。测试6 ARCH-01 同样已由 v1.5.1 WP5 copy+stub 机制覆盖。

### 0.3 「53 个死链」—— 主要为测试环境产物

测试5 称全库 53 死链，分布：

## 2. WP1 · 被调用方契约与衔接硬化（P0）

### 2.1 问题

测试5/6 反复报告「调 agent 需手动模拟」。经 §0.1 校准，根因不是「agent 不可执行」，而是**被调用方 SKILL 未声明「被调用契约」**：

- research-agent SKILL 未明确「ingest 调用我抽取原子观点时，应返回什么 JSON 结构」
- memory-agent SKILL 未明确「advisor 调用 recall_similar 时，应返回排序后的笔记列表 + 相似度分数」
- manager-agent SKILL 未明确「ingest 调用 detect_conflicts 时，应返回冲突对清单」

导致调用方（ingest/goal/project/advisor/connect）只能凭语义猜测返回结构，运行不稳定。

### 2.2 方案

#### 2.2.1 在 3 个 agent SKILL 顶部增加「§0 被调用契约」段

每个 agent SKILL 新增 frontmatter 后的首段，声明所有 intent 的**调用入参 + 返回结构**。示例（research-agent）：

```markdown
## 0. 被调用契约

### extract_atoms
- 入参：{ source: "<inbox 笔记路径>", scope: "frontmatter+body" }
- 返回：{
    atoms: [{ claim: "...", confidence: 0-100, maturity: "captured" }],
    suggested_relations: [{ type: "supports|evolves|...", target: "[[X]]" }],
    tags: ["<受控词表内>"],
    dedup_hits: [{ against: "[[Y]]", strategy: "merge|skip|keep" }]
  }

### cross_verify
- 入参：{ atom: "<claim>", against_domains: ["ai-engineering"] }
- 返回：{
    verdict: "supports|contradicts|evolves|unrelated",
    evidence: ["[[note-1]]", '[[note-2]]'],
    suggested_relation: { type: "...", target: "[[X]]" }
  }
```

#### 2.2.2 调用方 SKILL 引用契约而非重述

ingest §4 步骤 4「调 research-agent 抽取原子观点」改为：

```markdown
调 quick-kb-research-agent intent=extract_atoms（入参/返回见该技能 §0 契约）。
将返回的 atoms 写入新笔记的 frontmatter.value 与正文原子观点段。
```

#### 2.2.3 验收

- 3 个 agent SKILL 均含 §0 被调用契约段
- 5 个调用方（ingest/goal/project/advisor/connect）的 agent 调用步骤均引用契约而非重述
- bench 用例覆盖：`ingest` 调 `extract_atoms` 后产出的笔记 frontmatter 完整率 100%

## 3. WP2 · ingest 全链路补强（P0）

### 3.1 问题

ingest 是技能链路的中枢，但存在 4 个真缺口：

| ID | 缺口 | 影响 |
|----|------|------|
| WP2-A | 入库后不调 connect §5.2.1 反向补全 → 目标笔记的反向键缺失 | 非对称关系图谱残缺，影响召回 |
| WP2-B | 入库后 inbox 素材未清理/标记 → 重复入库风险 | inbox 积压 |
| WP2-C | import 写入 inbox 后未触发 ingest → 导入素材滞留 | 测试5/6 均报告 import→ingest 断链 |
| WP2-D | ingest 写入时未强制 inline-array tags 格式 | normalize 才能修复（v1.5.0 WP2 已加 schema 校验，但写入端未硬化） |

### 3.2 方案

#### 3.2.1 ingest §4 新增步骤 4.5「关系反向补全」

```markdown
### 步骤 4.5 · 关系反向补全（v1.7）

对每条新增笔记的 relations.supports / evolves / supersedes：
- 复用 quick-kb-connect SKILL §5.2.1 的反向补全表
- 在目标笔记 frontmatter 写入对应反向键
- 幂等：已存在不重复追加
- 写入失败（目标笔记不可写）→ 仅在报告列「⚠ 反向补全失败清单」，不阻断入库
```

#### 3.2.2 ingest §4 新增步骤 4.6「inbox 素材归档」

```markdown
### 步骤 4.6 · inbox 素材归档（v1.7）

入库成功后，对源 inbox 笔记：
- 在 frontmatter 追加 `status: ingested` + `ingested_to: "[[02_areas/...]]"`
- 移动到 `00_inbox/_processed/<原子目录>/`（保留 mtime）
- 不删除（保留追溯链，需归档时调 archive）
```

#### 3.2.3 import SKILL 新增「ingest 触发提示」

import 写完 inbox 后，在输出末尾**强制建议**：

```markdown
> 已导入 N 条到 00_inbox/_imports/<source>/。
> 下一步：调用 quick-kb-ingest（scope=00_inbox/_imports/<source>/）将其入库。
> （import 不自动触发 ingest，避免批量导入时一次性 ingest 失败回滚困难）
```

**设计决策**：不自动触发，因批量导入时单条失败会回滚整批。改为强提示 + 提供 scope 参数。

#### 3.2.4 ingest 写入端强制 inline-array tags

ingest §4 步骤 2.1「字段补全」增加：

```markdown
- tags 必须为 inline array 格式 `[tag1, tag2]`，禁止 YAML block list 格式
- 写入前检测：若为 block list → 自动转换
```

### 3.3 验收

- bench ingest 用例：入库后目标笔记含反向键的比例 ≥ 95%
- inbox 周转时长：ingest 后 100% inbox 素材进入 `_processed/`
- 新建笔记 tags 格式 100% inline-array

## 4. WP3 · 数据完整性约束（P1）

### 4.1 问题

| ID | 问题 | 当前状态 |
|----|------|---------|
| WP3-A | 双向 evolves 循环（A evolves B 且 B evolves A） | connect 无循环检测 |
| WP3-B | supports + contradicts 共存于同一对笔记 | connect/ingest 无冲突消歧 |
| WP3-C | contradicts/evolves/supersedes 全库稀疏（测试5：96/6/1/0） | 无自动推荐机制 |
| WP3-D | experience 类型全缺 outcome 字段 | 模板未硬约束 |

### 4.2 方案

#### 4.2.1 connect §5.2.1 新增「循环检测」

写入 A→B 前检测 B 是否已含 A→B 或反向 evolves：
```markdown
若检测到循环：
- 不写入
- 报告：「⚠ 关系循环：A evolves B 与 B evolves A 冲突，请改用 supersedes 或拆分」
- 建议用户手动消歧
```

#### 4.2.2 connect / ingest 新增「冲突消歧」

写入 supports 或 contradicts 前，检测同一对笔记是否已有反向关系：
```markdown
若 A.supports=[B] 已存在，新写 A.contradicts=[B]：
- 暂不写入 contradicts
- 报告：「⚠ 语义冲突：A 对 B 已 supports，是否覆盖？需补充 context」
```

#### 4.2.3 connect 新增「evolves/supersedes 候选推荐」

build_moc 时，对同 domain + 同 type 的笔记对，若 tag Jaccard ≥ 0.7 且 created 时间差 > 30 天，标记为 evolves/supersedes 候选（不自动写入，仅提示）。

#### 4.2.4 模板：experience 补 outcome 字段

`templates/{zh,en}/experience.md` 新增必填字段：
```yaml
outcome: ""  # 正面/负面/中性 + 简述结果
trigger: ""  # 触发情境（供 detect_repeat_mistakes 用）
```

`references/frontmatter-v0.2.md` §2 同步声明。

### 4.3 验收

- bench connect 用例：循环关系 100% 被拒绝
- bench ingest 用例：supports+contradicts 共存场景触发消歧提示
- experience 笔记 outcome 字段填写率 ≥ 90%

# Slug 命名规则

## 规则
1. 文件名 = basename + `.md`，basename 用 kebab-case
2. 中文标题：保留中文（不转拼音），用 kebab-case 分词（如 `混合检索设计.md` → `混合检索设计.md`，已是合法）

3. 长度限制：basename ≤ 50 字符（中文计 1 字符）
4. 禁止字符：空格（→ `-`）、`/`、`\`、`:`、`*`、`?`、`"`、`<`、`>`、`|`
5. 数字前缀：仅允许日期前缀（`2026-08-14-...`）和 inbox 序号（`inbox-001`）
```

```

## 8. WP7 · 导入与归档协议完善（P2）

### 8.1 问题

| ID | 问题 |

### 8.2 方案

#### 8.2.1 import 量纲自动转换

import SKILL §字段映射增加：
```markdown
- confidence ∈ (0, 1] → 视为 0-1 量纲，× 100 取整
- confidence > 1 → 视为 0-100，保留
- confidence 缺失 → 默认 60（外部文档未经验证）
- 在 import-report 标注每条迁移：「obsidian confidence 0.8 → 80」
```

#### 8.2.2 import 支持 dry-run

import SKILL 新增 `action` 参数：
```markdown
| action | 否 | run | run / dry-run（仅输出预览报告，不写文件） |
```

#### 8.2.3 archive goal/project status 传播

archive SKILL §归档步骤新增：
```markdown
归档 goal 时：
- 扫描 goal frontmatter.linked_projects（若存在）
- 对每个关联 project：
  - 若 project status=active → 在报告提示「⚠ 关联 project <X> 仍 active，是否一并归档？」
  - 不自动归档（避免误操作），仅提示
```

#### 8.2.4 project archive lesson 派生半自动化

project archive 时：
```markdown
扫描项目 decisions/ 目录的 ADR 文件，提取 actual / lesson 字段（若已填）。
对每条含 lesson 的 ADR：
- 在 07_principles/<domain>/ 生成 experience 笔记草稿（type: experience, outcome: ADR.actual, trigger: ADR.context）
- 草稿 status: draft，需用户确认后 status: active
```

### 8.3 验收

- bench import 用例：confidence 量纲迁移 100% 自动
- import dry-run 不产生任何 vault 变更
- project archive 后 07_principles/ 含对应 experience 草稿
