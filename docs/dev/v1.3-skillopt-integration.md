## 0. TL;DR

quick-knowledge 目前 4 个 CI job 全部是**静态结构校验**（frontmatter 字段、wikilink 死链、占位符残留、demo-vault 目录），**零行为测试**——CI 无法回答「用户说『记一下 cache 方案有问题』时，capture 是否真的写到 `00_inbox/ideas/` 并打 `type: idea`」。

本设计引入 **[microsoft/SkillOpt](https://github.com/microsoft/SkillOpt)**（文本空间技能优化器，MIT，PyPI `skillopt`）作为**行为评测 + 技能文本优化**引擎：

1. 写一个自定义 SkillOpt benchmark `quickkb`，把 14 个 SKILL.md 当作「被优化的权重」
2. 用 demo-vault 作为 ground truth，rollout = 跑技能 → 检查产物（路径 / frontmatter / citation）
3. SkillOpt 的 `Rollout → Reflect → Aggregate → Select → Update → Gate` 流水线自动产出 `best_skill.md`
4. 永不自动部署——产出物供人工 review 后单独 commit

**MVP（v1.3.0）**：仅 `quick-kb-capture` × 20 golden cases × mock 后端，验证「能跑通」。
**v1.3.1**：扩展到 query + ingest。
**v1.4**：接入 SkillOpt-Sleep 真实会话闭环（先过隐私 ADR）。

## 2. SkillOpt 背景

### 2.1 是什么

**SkillOpt** 是 Microsoft 开源的「文本空间技能优化器」。核心类比：

| 神经网络 | SkillOpt |
|---------|---------|
| 权重 (weights) | skill markdown 文档 |
| 前向传播 (forward) | rollout（跑技能） |
| 梯度 (gradient) | reflect（反思轨迹） |
| 梯度剪裁 (clipping) | select（编辑选择） |
| 验证集 (validation) | held-out gate |
| 多轮 epoch | 多轮 update |

输出物：`best_skill.md`（300-2000 tokens），部署到**冻结的目标模型**上。

### 2.2 双引擎

| 引擎 | 命令 | 在 quick-knowledge 的用途 |
|------|------|--------------------------|
| **SkillOpt 研究引擎** | `skillopt-train` / `skillopt-eval` | 在自定义 `quickkb` benchmark 上做有监督的 SKILL.md 优化 |
| **SkillOpt-Sleep** | `skillopt-sleep` | 夜间回顾本地 Claude Code 真实会话，挖掘反复出现的 capture/daily pattern，长出 SKILL.md 的「经验补丁」（**v1.4 接入**） |

两个引擎独立可选用。

### 2.3 6 阶段流水线

```
Rollout → Reflect → Aggregate → Select → Update → Gate
```

| 阶段 | 在 quick-knowledge 语境下 |
|------|-------------------------|
| Rollout | 用当前 SKILL.md 作 system context，对一批 golden case 跑 quick-kb-{skill}（例如「记一下 X」→ 看 capture 写出什么文件） |
| Reflect | 优化器读 `conversation.json` 轨迹，找出哪里出错（source 类型识别错 / frontmatter 缺字段 / 路径走错） |
| Aggregate | 多条反思合并成对 SKILL.md 的编辑提案 |
| Select | 在多个候选编辑中按得分剪裁 |
| Update | 把选中的编辑合并进 SKILL.md |
| Gate | 在 held-out 验证集上跑一次，不过就回滚（防过拟合） |

### 2.4 自定义 benchmark 契约

SkillOpt 内置 6 个 benchmark（DocVQA/ALFWorld/OfficeQA/SearchQA/SpreadsheetBench/LiveMathematicianBench）**与 PKB 场景无关**——都是「外部任务 QA」范式，无法验证「文件真的被写到对的地方」。

但 SkillOpt 暴露了自定义 benchmark 接口（`docs/guide/new-benchmark.md`），需实现 **4 件套**：

1. **`SplitDataLoader` 子类** — 加载 train/val/test 用例
2. **rollout helper** — 跑目标模型，把每次对话轨迹持久化到 `<rollout_dir>/predictions/<id>/conversation.json`
3. **`EnvAdapter` 子类** — 接线 dataloader + rollout 到 SkillOpt 生命周期
4. **YAML config** — 引用 env + 标准 train/optimizer/gradient 旋钮

**关键约束**：
- 打分逻辑写在 rollout helper（没有 `evaluate()` ABC）；`hard`（0/1 或 [0,1]）+ `soft`（[0,1]）是优化器唯一信号
- 必须持久化 conversation.json，否则 reflect 无法生成补丁
- 参考样板：`skillopt/envs/officeqa/`（最简完整实现，~200 行）

### 2.5 后端选择

| 后端类型 | 选项 | 适用性 |
|---------|------|-------|
| chat | `openai_chat` / `claude_chat` / `qwen_chat` / `minimax_chat` / `openai_compatible` | 把 SKILL.md 当 system prompt 单轮对话。简单但失真（技能实际跑在 Claude Code 里有文件读写） |
| exec | `claude_code_exec` / `codex_exec` | 真实复现：起 Claude Code 子进程，让技能真的写文件到 vault 副本。**MVP 首选** |

### 2.6 SkillOpt-Sleep 安全边界（v1.4 提前标注）

- **本地只读收割**：harvest 本地 `~/.claude/projects/` / `~/.codex/` / `~/.cursor/` 等会话 JSONL
- **mock 后端零网络**：`skillopt-sleep dry-run --backend mock` 不发任何 provider 请求
- **真实后端会把截断的会话发给 provider**——必须先 `harvest` → 人工 review/redact → 标 `"reviewed": true` → 才能用 real backend replay
- **v1.3 完全不接入 Sleep**；v1.4 启动前必须先过 ADR-018 隐私设计

### 4.2 单次 rollout 数据流

```
golden case (input: "记一下 cache 方案有问题")
   │
   ▼
QuickkbDataLoader.load_split_items() → item dict
   │
   ▼
rollout.run_batch(items, skill_content=current_SKILL_md)
   │
   ├── clone-vault.mjs → 临时 demo-vault 副本（不动 ground truth）
   │
   ├── claude_code_exec 后端
   │     system = current_SKILL_md
   │     user   = item.input
   │     cwd    = 临时 vault 副本
   │
   ├── 技能执行：写文件到副本 vault
   │
   ├── scoring/ 评分：
   │     frontmatter.py → 检查写入文件 frontmatter 字段
   │     routing.py      → 检查写入路径匹配 expected_path_glob
   │
   ├── 写 conversation.json（reflect 必需）
   │
   └── 返回 {id, hard, soft, predicted_answer, ...}
```

### 4.3 评分器设计

每个评分器返回 `(hard: float, soft: float)`：
- **hard** 取最严 fail-fast（任一 0 即 0）——是否完全正确
- **soft** 取加权平均——部分正确程度（让优化器即使 hard=0 也有梯度方向）

**`routing.py`** — 路径评分

```python
def score(actual_path: str, expected_path_glob: str) -> tuple[float, float]:
    """例：expected '00_inbox/ideas/*.md'"""
    match = fnmatch(actual_path, expected_path_glob)
    return (1.0, 1.0) if match else (0.0, 0.0)
```

**`frontmatter.py`** — 字段评分

```python
def score(actual_fm: dict, required_fields: dict) -> tuple[float, float]:
    """required_fields 例：{type: '^idea$', title: '.*cache.*'}"""
    score_per_field = []
    for k, expected_regex in required_fields.items():
        actual = actual_fm.get(k)
        ok = bool(actual and re.match(expected_regex, str(actual)))
        score_per_field.append(1.0 if ok else 0.0)
    hard = 1.0 if all(score_per_field) else 0.0
    soft = sum(score_per_field) / len(score_per_field)
    return hard, soft
```

**`citation.py`**（v1.3.1） — query 命中度

```python
def score(answer: str, ground_truth_ids: list[str]) -> tuple[float, float]:
    cited = extract_wikilinks(answer)
    hit = len(set(cited) & set(ground_truth_ids))
    return (1.0, hit / len(ground_truth_ids)) if hit else (0.0, 0.0)
```

## 6. 关键设计决策与权衡

### 6.1 为什么写自定义 benchmark 而非用内置？

SkillOpt 内置 benchmark 全是「外部 QA」范式，无法验证「文件真的被写到对的地方」。`officeqa` 最接近但仍是 QA，无法表达「检查 capture 是否把 idea 写到了 `00_inbox/ideas/`」这类路径断言。

### 6.2 为什么 MVP 用 mock 后端？

- **成本**：3 epoch × 8 batch × 20 case = 480 次 LLM 调用，真实跑约 $5-20，MVP 不值得
- **稳定性**：真实后端有 rate limit / 网络抖动 / Claude Code CLI 版本漂移
- **目的错位**：MVP 是验证「能跑通」不是「能优化」，mock 够用

### 6.3 为什么 best_skill.md 永不自动部署？

SkillOpt gate 是「相比 baseline 提升 5%」，但**不能保证语义不漂移**——优化器可能为了刷分让 capture 变保守（写更少字段以提高 frontmatter 完整率），与产品意图相反。永远人工 review diff 后单独 commit。

### 6.4 为什么不一开始就上 SkillOpt-Sleep？

Sleep 涉及**收割本地会话**，存在隐私敏感面（即使 mock 后端，harvest 也读 `~/.claude/projects/`）。必须先：
- 写清楚数据流 ADR（哪个进程读哪些文件、传给谁）
- 默认 `--redact` 开启
- 用户显式 opt-in `--backend real`

→ v1.4 的活，不在 v1.3 MVP。

### 6.5 与现有 v0.1-v1.2 测试的关系

| 现有测试 | SkillOpt 评测 | 关系 |
|---------|-------------|------|
| `check-frontmatter.mjs` | `scoring/frontmatter.py` | **互补**：CI 抓静态违规，SkillOpt 抓动态生成质量 |
| `check-links.mjs` | （v1.3.1 加 `scoring/link.py`） | 同上 |
| demo-vault placeholder check | gate 用 demo-vault 作 ground truth | 复用 demo-vault |

**SkillOpt 评测不替代任何现有测试，只做加法。**

## 8. Capture MVP · Golden Cases 完整设计（45 个）

### 8.1 设计原则

1. **从设计文档反推**：每个 case 必须能追溯到 `skills/quick-kb-capture/SKILL.md` 的某条具体行为约束（步骤/边界/降级/自检项），不是凭空想象
2. **维度化覆盖**：9 个测试维度，每个维度至少 2 个 case（详见 §8.3 覆盖矩阵）
3. **真实输入**：禁用「测试 case 1」「foo bar」等模板词；每个 input 是用户真实可能说出的话
4. **可机器评分**：每个 case 必须能由 `routing.py` + `frontmatter.py` + `behavior.py`（新增）自动判分
5. **包含负面 case**：去重、降级、不触发、注入防御等「不应发生」的断言同样重要

#### J · 流程衔接 / 端到端（6 个 · 7 阶段流程）

> **设计原则**：用同一个种子输入走完「输入→沉淀→目标→执行→产出→索引→系统」全程，验证相邻技能之间的数据契约。每个 case 测试一个过渡，检查下游技能能否正确消费上游产物。
>
> **种子输入**（贯穿 J1-J6）：用户 capture 一条「记一下 RAG chunking 大小影响检索召回」idea，全程跟踪这条数据如何流经 7 阶段。
>
> **实现策略**：fixture-based 而非真实多技能编排——预先准备 demo-vault 的某个中间状态，运行单个技能，检查产物对下游是否可消费。

| J3 | `flow-goal-to-execution` | 目标→执行 | J2 的 goal + atom | project `04_projects/rag-poc/decisions/YYYY-MM-DD-chunk-size.md` 的 Decision Ledger 引用 goal + atom；decision 含 `context` 字段记录决策依据 | **决策可回溯**：project 决策链能追到 goal + atom，不丢失上下文 | project §3 + DESIGN §6.6 |
| J4 | `flow-execution-to-output` | 执行→产出 | J3 的 decision | daily `05_outputs/daily/YYYY/MM/YYYY-MM-DD.md` 的「做了什么」段含 wikilink 指向 project 或 decision；vague entry 触发反问机制 | **进展自动捕获**：daily 不只记用户输入，还识别 project 进展 | daily §3 + SKILLS_SPEC §8 |
| J5 | `flow-output-to-index` | 产出→索引 | J4 的 daily | MOC `06_wiki/mocs/rag-architecture.md` 收录 daily 中提到的 atom；query「RAG chunking」检索能命中 atom + daily | **索引连贯**：MOC 自动维护 + query 跨目录检索不打断层 | connect §4 + query §3 |
| J6 | `flow-index-to-system` | 索引→系统 | J5 的 MOC + atom | review `05_outputs/reviews/weekly/YYYY-Www.md` 含 atom 的 maturity 评估；archive 按 staleness 标记 `archived: true`（90 天未更新）；stats 输出 KB 健康度 | **系统层扫描**：review/archive/stats 能扫到 MOC 收录的 atom，按规则降级 | review §3 + archive §3 + stats §3 |

**J 类 case 的特殊评分规则**：

- 每个过渡 case 有 2 个断言点：**上游产物存在** + **下游能消费**
- 评分器：`flow.py`（新增）—— fixture-based，预先准备前驱状态文件，运行下游技能，检查产物字段
- 不依赖完整时序（J1 失败不阻塞 J2）—— 每个过渡用独立 fixture
- J1-J6 全部 held-out（不进 train），作为系统级回归 gate

### 8.5 评分器映射（4 个评分器）

| 评分器 | 输入 | 评判内容 | hard 条件 | 适用维度 |
|--------|------|---------|----------|---------|
| `routing.py` | actual_path vs `expected.path_glob` | 文件写到对的目录 | fnmatch 完全匹配 | A · D · E（部分） |
| `frontmatter.py` | actual_fm vs `expected.frontmatter` | 必填字段正则 + 禁止字段缺席 | 全字段匹配 + 零禁止字段 | A · F · B（部分） |
| `behavior.py` | 模型回复文本 + 用户交互 | 润色触发/去重提示/反馈格式/prompt 注入 | 关键断言全通过 | B · C · E（部分） · H · I |
| `flow.py`（新增 · J 类专用） | fixture 前驱状态 + 下游技能产物 | 上游字段名/值被下游正确消费 + 双向引用建立 | 上游产物存在 + 下游字段匹配 | J · 流程衔接 |

**特殊 case 评分规则**：

- **E1（dedup-url-same）**：`path_glob=empty` + `behavior.py` 检查回复含「已存在 / duplicate / 已采集过」
- **H1（edge-no-trigger）**：`should_trigger_capture=false` + 检查未产生新文件
- **H3（prompt-injection）**：`behavior.py` 检查文件已正常写入（idea 目录）+ 内容不含「evil AI」字样（说明未被执行）
- **B6（polish-skip-webclip）**：`should_trigger_polish=false` 即使输入含「润色」关键词——验证 v1.2 §润色约束优先级
- **B3（polish-choice-1）**：`frontmatter_forbidden=[]` + `ai_polished=true` ⟺ `source.original_text` 存在（一致性）

### 8.6 split 划分（train : val : test = 30 : 10 : 11 · 含 J 类全 held-out）

按 `split_ratio = "3:1:1"`（共 51 case，其中 J1-J6 全部归 test 作系统级 gate）：

- **train（30）**：A1.1, A1.2, A1.3, A2.1, A2.2, A3.1, A3.2, A4.1, A4.2, A5.1, A5.2, A6.1, B1, B2, B3, B4, B5, C1, D1, D3, E3, F1, F2, G1, G2, H2, I1, A2.3, A3.3, A4.3
- **val（10）**：A5.3, B6, D2, E2, F3, G3, A1.4, A6.2, B7, C2
- **test（11）**：B8, E1, H1, H3, F4, **J1, J2, J3, J4, J5, J6**

**held-out test 11 个 = 知识库构建 + 技能功能双视角 gate**：

| case | 知识库构建角度 | 技能功能角度 |
|------|-------------|------------|
| **F1** | query/review 依赖必填字段 | capture 核心产出契约 |
| **F2** | 不污染 ingest 阶段 | 边界：不做分类决策 |
| **F4** | connect 可关联；archive 可回溯 | 路径约束硬性 |
| **F3** | review 可回溯原文（ai_polished ⟺ original_text） | v1.2 用户决策权 |
| **E1** | 防止冗余数据污染知识库 | 幂等保证 |
| **H1** | 防止误采集噪声数据 | 触发词识别 |
| **H3** | 防止 prompt 注入污染数据 | 安全关键 |
| **B8** | 润色不实质扩展时保留原文（数据保真） | v1.2 自动判定 |
| **J1** | capture→ingest 数据契约（field 名/值可消费） | 输入→沉淀过渡 |
| **J2** | ingest→goal 双向引用建立 | 沉淀→目标过渡 |
| **J3** | goal→project 决策链可回溯 | 目标→执行过渡 |
| **J4** | project→daily 进展自动捕获 | 执行→产出过渡 |
| **J5** | daily→MOC/query 索引连贯 | 产出→索引过渡 |
| **J6** | MOC→review/archive/stats 系统层扫描 | 索引→系统过渡 |

→ 前 8 个验证**单点行为不退化**，后 6 个（J 类）验证**数据流转契约不破裂**——SKILL.md 改动后如果 J 类失败，说明改动破坏了下游技能的消费能力，必须回滚。

### 8.7 Case 写作禁忌

| ❌ 禁止 | ✅ 应该 | 原因 |
|--------|--------|------|
| 输入用「测试 idea 1」「test case」等模板词 | 用真实用户会说的话 | 防过拟合到模板 |
| 把 SKILL.md 术语搬进 case（如「type=idea 的 idea」） | 用户视角的自然语言 | 测的是 SKILL.md 是否被理解 |
| 所有 case 长度都接近 | 长短差异要大（5 字 ~ 200 字） | 覆盖字符数边界 |
| 只覆盖 happy path | 必须含 E/G/H 类负面 case | 降级/边界才是回归测试核心 |
| expected 直接抄 SKILL.md 路径表 | 从用户视角反推「这个输入应该写到哪」 | 测语义不是测字面 |
| case 缺 `references` 字段 | 每个 case 必须溯源到 SKILL.md 具体段 | 便于回归时定位变更 |
| 评分器过严（hard 全 0） | soft 分始终在 [0,1] 提供梯度 | 避免优化器卡死 |

## 9. 风险与缓解

| 风险 | 等级 | 缓解 |
|------|-----|------|
| **R1** SkillOpt 上游 API 漂移（v0.2 → v0.3 改 EnvAdapter 接口） | 中 | 锁版本 `skillopt==0.2.*`；adapter 层加抽象 |
| **R2** Claude Code CLI 版本与 `claude_code_exec` 后端不匹配 | 中 | CI 用 `claude-code@latest`，本地用项目 pinned 版本；rollout 加 sanity check |
| **R3** mock 后端测出的优化在真实环境失效 | 高 | MVP 明确「不部署」；v1.3.1 加 nightly 真实 backend 对照 |
| **R4** Golden case 偏，过拟合到 case | 中 | val/test held-out；case 写作遵循「真实用户会怎么说」原则 |
| **R5** 评分器过严（hard 全 0）→ 训练不收敛 | 中 | soft 分始终有梯度；MVP 先 eval 不 train |
| **R6** SkillOpt-Sleep 隐私泄露（v1.4 提前标注） | 高 | v1.3 完全不接入；v1.4 启动前必须过 ADR-018 |
| **R7** 部署 best_skill.md 后行为退化 | 高 | 永远人工 review；commit message 必须引用 report.md |
