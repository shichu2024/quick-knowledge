## 0. 测试报告校准（必须先读）

测试报告整体专业度高（问题分级、影响技能、修复建议齐全），但有 5 类系统性误差，**不能直接照单修复**：

### 0.1 「8 个 agent 全部 available: false」—— 测试环境产物

报告反复引用 `kb.config.yaml` 中 `research-agent / memory-agent / manager-agent / query-agent / review-agent / stats-agent / archive-agent / capture-agent` 全部 `available: false`。

**真相**：
- 现行 `examples/demo-vault/99_system/config/kb.config.yaml` **根本没有 agents 配置段**。
- v1.4 重构后（commit `95f8afe`），3 个 agent（manager / memory / research）已**独立为 skill**，随技能包分发，不再由 config 开关。
- 报告中另外 5 个「agent」（query / review / stats / archive / capture）**从来不是 agent**，是业务技能自身的能力。测试者把「技能需要做语义检索」误读为「依赖 query-agent」。

**处置**：报告中所有基于「agent 不可用 → 降级」的 P0/P1 条目，**降级为测试环境问题**，不进 v1.5。但衍生的真问题（如「降级路径未写进 SKILL」）保留，见 WP8。

### 0.2 「P0-1 templates/{zh,en}/project.md 不存在」—— 事实错误

**真相**：`templates/zh/project.md` 与 `templates/en/project.md` **都存在**（已验证）。init SKILL §3.2 明确要求把它们复制到 vault 的 `99_system/templates/{zh,en}/`。

**测试根因**：测试 vault 的 `99_system/templates/` 未同步完整（可能用旧版 init 初始化，或手工删过）。属于 vault 维护问题，不是 spec bug。

**处置**：P0-1 删除。但暴露了一个真问题——init 缺少「模板完整性校验 + 自检失败时自动补齐」的强约束（现 §6 自检清单只列了条目数，未防漏），见 WP1。

### 0.3 「init MOC 引用 embedding-strategies 等不存在的笔记」—— 测试环境产物

报告称 init 创建的 area MOC 含大量预设笔记名导致死链。

**真相**：现行 init SKILL §3.6 `02_areas/<domain>/_moc.md` 模板用的是**占位符**：

```markdown
## 主题
- _（待填充）_

## 待补充
- [ ]
```

不含任何预设笔记名。测试 vault 的 MOC 内容系测试者手工填入或来自更早版本。

**处置**：P1-1 删除。connect 死链的真因是测试者自己写的占位 wikilink，不是 init 产物。

### 0.4 「normalize relations 用 dict，vault 用 list」—— 因果倒置

报告称 spec 与 vault 冲突，建议统一为 list。

**真相**：`references/frontmatter-v0.2.md` §3 明确规范为 **dict 格式**（`relations: { supports: [...], contradicts: [...] }`），所有 SKILL（connect / ingest / normalize）均遵守。测试 vault 若出现 list 格式 `[{type, target}]`，是**笔记写错了**，不是 spec 歧义。

**处置**：P1-12 改写——真问题不是「spec 歧义」而是「缺校验」，归入 WP3。

### 0.5 「P0-3 agent 降级机制普遍缺失」—— 部分过时

报告称 12/14 技能缺降级专节。

**真相**：现行 14 个 SKILL 中，**12 个已有 §降级路径 段**（init / capture / ingest / daily / goal / project / connect / query / stats / review / advisor / archive 经核查均有）。报告基于的测试版本可能更早。

**真问题**：少数 SKILL 的**自检清单**仍把「调 agent」列为必选，与降级路径矛盾（如 project §10 update 自检未明确降级态）。这是细节问题，归入 WP8。

## 2. WP1 · 模板与 init 完整性校验（中优先级）

### 问题

- **WP1-1**：init 自检清单只校验「`99_system/templates/{zh,en}/` 各 12 个文件」，但**未校验文件内容完整性**。若用户误删某模板的部分字段，init upgrade 不会发现。
- **WP1-2**：project SKILL §3 输入表写「默认 `templates/{zh,en}/project.md`」但未说清楚这是**仓库源模板**还是 **vault 内 `99_system/templates/` 的副本**——技能执行时应读后者。

### 修复方案

1. init §3.7 upgrade 子流程增加「模板字节级 diff」：对每个模板文件计算 SHA-256，与仓库源比对，不一致则在 upgrade 报告标 ⚠ 并询问是否覆盖。
2. init §7 自检清单加一项：
   ```
   - [ ] 24 个模板文件 SHA-256 与仓库源一致（upgrade 场景）
   ```
3. project / goal / daily / decision 等所有引用模板的 SKILL，统一表述为「读 `99_system/templates/{lang}/<name>.md`（由 init 铺设）」。

### 验收

- 手动删除某模板的一个字段 → init upgrade 能识别并报告。
- project SKILL 执行时模板路径无歧义。

## 3. WP2 · confidence 量纲全局统一（高优先级 · 系统性）

### 问题（这是报告中最严重的真问题）

当前 repo confidence 量纲**事实不一致**：

| 位置 | 量纲 | 证据 |
|------|------|------|
| `research-agent/SKILL.md` §2.2 | **0-100** | `单一非一手来源 → 30-40 / 多源佐证 → 60-75` |
| `quick-kb-ingest/SKILL.md` L114 | **0-100** | `单源 30-40 / 多源 60-75 / 一手 80-95` |
| `quick-kb-normalize/SKILL.md` L80 | **0-100** | `confidence 缺失 → 50（默认）` |
| `quick-kb-stats/SKILL.md` §3 | **0-100** | 直方图 `0-30 / 31-60 / 61-85 / 86-100`；`confidence < 60`；`confidence ≥ 70` |
| `quick-kb-manager-agent/SKILL.md` KS 公式 | 隐含 0-100 | `KS = confidence × log2(1 + reuse) × impact` |
| `quick-kb-import/SKILL.md` L131 | **0-1** | `若在 [0,1] 保留；若在 (1,100] 则除以 100 归一；缺失默认 0.5` |
| `examples/demo-vault/.../kb.config.yaml` | **未声明** | 无 confidence 字段定义 |

`frontmatter-v0.2.md` 也未显式声明量纲。报告里 query 用 `confidence / 100` 排序说明 query 假设 0-100。

### 决策

**全局统一为 0-100 整数量纲**（理由：现有 5 处 spec 已用 0-100，只有 import 用 0-1；改 import 一处比改 5 处成本低；且 0-100 在 LLM 推理时分辨率更高）。

### 修复方案

1. `references/frontmatter-v0.2.md` §2 字段表加一行：
   ```
   | confidence | 0-100 整数（0=纯推测，100=一手实验/官方文档） | 必填（concept/resource/belief） |
   ```
2. `quick-kb-import/SKILL.md` L131 改为：
   ```
   confidence: 原 confidence 若在 [0,100] 保留；若在 (0,1] 则 ×100 取整；缺失默认 50
   ```
3. KS 公式（manager-agent / stats）保持 `confidence × ...` 不变（已是 0-100 量纲）。
4. 所有 SKILL 中出现的 confidence 阈值（如 `confidence < 60`）统一加注释「0-100 量纲」。
5. `quick-kb-normalize` 增加一项：扫描 vault 内所有 confidence 字段，若 `< 1` 则标 ⚠「疑似 0-1 量纲，需 ×100」，写入 diff log 待用户确认。

### 验收

- 新建一条 import 笔记，confidence = 0.85 → 自动转 85。
- stats 直方图不再出现量纲混乱。
- KS 公式输出合理（不再因量纲错误产生巨大或微小值）。

## 4. WP3 · frontmatter schema 校验机制（高优先级 · 系统性）

### 问题

报告 P0-4 提出的「6 种 frontmatter 变体」严重程度被夸大（实际 spec 一致），但暴露了真问题：**spec 有，但无校验**。用户/测试者写错格式时无人拦截。

- **WP3-1**：缺全局 JSON Schema 文件，无法被 SKILL 引用做校验。
- **WP3-2**：normalize 是事实上的 schema 迁移工具，但未声明这一点，也未提供「dry-run schema 校验」独立子动作。
- **WP3-3**：`source` 字段在 ingest / import 间确实 schema 略有差异（ingest `{type, url, note}`，import `{kind, original_path, imported_at}`），需统一。

### 修复方案

1. 新建 `references/frontmatter-schema-v1.json`（JSON Schema），覆盖：
   - 必填字段：title / type / created / updated / domain
   - 类型特定字段：concept 有 maturity，belief 有 evidence_strength 等
   - relations 强制 dict + 4 子键
   - confidence 强制 integer 0-100
   - source 用统一 schema：`{type: web|pdf|book|meeting|ai_dialog|reading, url?, path?, note?, captured_at}`
2. init §3.2 把 schema 文件复制到 vault `99_system/config/frontmatter-schema.json`。
3. normalize 增加独立子动作 `schema_check`（不修改文件，只输出违规清单）：
   ```
   quick-kb-normalize action=schema_check
   → 输出违规笔记清单 + 违规字段 + 修复建议
   ```
4. import 的 `source` 字段迁移到统一 schema（`{type, url?, path?, captured_at}`，废弃 `kind` / `original_path` / `imported_at`）。

### 验收

- 手写一条 `relations: [{type, target}]` 格式的笔记 → `normalize action=schema_check` 能识别。
- 新建笔记的 source 字段统一。

## 5. WP4 · project Decision Ledger 与派生闭环（高优先级）

### 问题

- **WP4-1**：Decision Ledger 命名两种共存：
  - project §6 step 2.1: `decisions/<YYYY-MM-DD>-<topic>.md`
  - project §4 step 6 init 示例: `decisions/<YYYY-MM-DD>-<topic>.md`
  - 但报告观察到测试中有 `decision-NNN-topic.md`（NNN 序号制）

  → **决策：统一为 `<YYYY-MM-DD>-<topic>.md`**（与 daily/progress 命名约定一致，可排序）。

- **WP4-2**：`derived_from` / `derived_to` 未声明为 list 还是 string。frontmatter-v0.2.md 未覆盖此字段。
- **WP4-3**：多对一派生（多个 decision 的 lesson 合并派生一条 experience）未在 spec 覆盖。现 §6 step 3「对每条 Decision Ledger 的 lesson」隐含 1:1。
- **WP4-4**：`outcome` 计算规则（success / failure / mixed）基于「关键字命中」，未列出关键字清单，实现时易漂移。
- **WP4-5**：归档前置门控（§6 step 1.5）列出「`actual: ""` 或 `lesson: ""` 拦截」，但未说 frontmatter 字段空字符串 vs 缺失字段的区别。

### 修复方案

1. project SKILL §3 输入表 + §4/§6 全局统一命名 `<YYYY-MM-DD>-<topic>.md`；自检清单加一项「文件名含日期前缀」。
2. `frontmatter-v0.2.md` 补充 `derived_from` / `derived_to` 字段定义：**YAML list of wikilink**（支持多对一）。
3. project §6 step 3 改写为支持多对一：
   ```
   3. lesson 派生 experience：
      3.1 对每条 Decision Ledger 的 lesson 判定是否与已派生的 experience 主题重合：
          - 若重合（同 domain + 同 lesson 主题词）→ 并入既有 experience，experience.derived_from 追加本 decision
          - 若不重合 → 新建 experience（原 1:1 流程）
      3.2 派生 experience 的 derived_from 必为 list，支持多 wikilink
   ```
4. outcome 关键字清单明示（写入 project SKILL §6 step 2.3）：
   ```
   success 关键字：超预期 / 显著好于 / 提前完成 / 优于 expected
   failure 关键字：未达成 / 显著差于 / 回滚 / 失败 / 延期严重
   mixed：部分 OK / 部分 miss / 混合
   ```
5. 归档门控明确：「字段缺失视为未回填，与空字符串等价拦截；`lesson: skipped` 是合法跳过值」。

### 验收

- 3 条 decision 中 2 条主题相同 → 派生为 1 条 experience，`derived_from` 含 2 个 wikilink。
- outcome 计算跨实现一致。

## 6. WP5 · archive move vs copy 语义定档（中优先级）

### 问题

- **WP5-1**：archive 「迁移目录」是 move 还是 copy+stub 未定档。报告观察到测试采用 copy+stub 但 spec 未写。
- **WP5-2**：「不改 relations」与「更新 wikilinks」边界不清——frontmatter 里的 `[[]]` 算 relations 还是 wikilink？
- **WP5-3**：归档 index 命名 `_index.md` vs `_archive-index.md` 不一致。

### 修复方案

1. archive SKILL §2 「做」段增加一条定档：
   ```
   - 归档采用 **copy + stub** 模式：
     · 原位置保留 stub 文件（frontmatter 加 `status: archived` + `redirect_to: [[98_archive/...]]` + 正文一行「已归档，见 [[...]]」）
     · 完整内容复制到 `98_archive/<type>/<slug>.md`
     · 理由：保留 wikilink 解析路径，断链率最低；stub 是显式标记，不依赖元数据
   ```
2. 明确边界：
   ```
   - 「不改 relations」指 relations 字段的语义结构不动（supports 仍 supports）
   - 「更新 wikilinks」指 relations 内的 target 字符串若指向被归档笔记，追加「(已归档)」后缀
   - 即：relations 的 type 不变，但 target 字符串可加后缀
   ```
3. 统一归档 index 命名为 `_archive-index.md`（比 `_index.md` 更明确，避免与目录默认索引混淆）。

### 验收

- 归档后原位置有 stub，含 `redirect_to`。
- 引用该笔记的 wikilink 自动加「(已归档)」后缀。

## 8. WP7 · capture/daily 衔接机制（中优先级）

### 问题

- **WP7-1**：capture 的 `type` 字段对所有源（idea/web-clip/reading/meeting/ai-dialog/pdf）都填 `idea`，无法区分。应加 `capture_type`。
- **WP7-2**：daily SKILL §步骤 1 说「自动生成 wikilinks」但未定义提取算法。
- **WP7-3**：daily 识别的「待入库项」无自动流转 ingest 的机制。

### 修复方案

1. capture frontmatter 加 `capture_type` 字段（枚举：idea / web-clip / reading / meeting / ai-dialog / pdf），ingest 时映射到 `type`（concept/resource）并丢弃 `capture_type`（或保留作溯源）。
2. daily §步骤 1 wikilink 提取算法明示：
   ```
   提取算法：
   - 扫描 02_areas/**, 03_goals/**, 04_projects/** 下所有 .md 文件的 basename
   - 对 daily 4 段内容做整词匹配（不区分大小写）
   - 命中即生成 [[basename]] wikilink
   ```

   ```
   📥 待入库 N 项：
   - [topic 1] → 运行 `quick-kb-capture ...` 或 `quick-kb-ingest ...`
   - [topic 2] → ...
   ```
   不自动触发（需用户确认），但提供一键命令。

### 验收

- capture 产出的 web-clip 含 `capture_type: web-clip`。
- daily 能自动把「RAG 调参」段链接到 `[[rag-tuning]]`（若该笔记存在）。

## 9. WP8 · 降级自检清单一致性（低优先级 · 系统性）

### 问题

报告 P1-7 指出：project §10 init 自检清单仍把「memory-agent 被调用」列为必选，与 §9 降级路径矛盾。

**核查结论**：不止 project。多个 SKILL 的自检清单未区分「正常态必选」与「降级态替代项」，导致降级执行时自检全红。

### 修复方案

所有 SKILL 的自检清单段引入统一的态标注格式：

```markdown
### create 自检
- [ ] （正常态）调 quick-kb-research-agent 生成学习路径
- [ ] （降级态 · 路径推荐失败）goal.md 段标注「⚠ 路径推荐失败，请手动填写」
- [ ] （二选一即可）
```

受影响 SKILL：goal / project / ingest / connect / advisor / review / normalize。

### 验收

## 10. WP9 · canvas / wikilink 规范化（低优先级）

### 问题

- **WP9-1**：connect SKILL 生成 `.canvas` 但未给 json-canvas schema。
- **WP9-2**：wikilink 命名约定（`[[文件名]]` vs `[[路径/文件名]]`）未全局声明，导致 stats 死链统计口径不一。
- **WP9-3**：archive 后 canvas 节点 id/file 路径未更新规则未定义。

### 修复方案

1. 新建 `references/json-canvas-schema.md`：定义节点 `id` / `type` / `file` / `label`，边 `id` / `fromNode` / `toNode` / `color`（按 relations 类型：supports=green / contradicts=red / evolves=blue / supersedes=orange）。
2. 新建 `references/wikilink-conventions.md`：
   - 默认 `[[文件名]]`（basename，不含扩展名）
   - 跨目录重名时 `[[路径/文件名]]`
   - 归档笔记 `[[文件名 (已归档)]]`
3. archive SKILL §4 增加 canvas 处理规则：归档笔记对应节点的 `file` 字段更新为 stub 路径，`label` 追加「(已归档)」。

### 验收

- connect 生成的 canvas 在 Obsidian 中可正确渲染。
- stats 死链统计口径与 wikilink 约定一致。
