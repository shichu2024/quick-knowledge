# quick-kb-daily

> 每日日志入口。**反问是增强不是阻塞** —— 用户只说一句话也能记录。

---

## 1. 何时调用

- 用户说「今天的日志」「记日志」「daily」「今天做了什么」
- 一天结束前回顾时
- 接续前一天的日志

## 2. v0.1 范围

### 做

- 加载/创建 `05_outputs/daily/YYYY/MM/YYYY-MM-DD-<summary>.md`（新建带 summary；同日已有旧文件 → 编辑不改名，详见 §步骤 1）
- 4 段拆分：做了什么 / 学到什么 / 想法 / 卡点
- **反问机制**（最多 2 轮，不变成问卷）
- wikilinks 自动抽取（识别已有笔记标题）
- 待入库项提示（建议调用 quick-kb-capture）
- frontmatter 用 v0.1 子集

### 不做

- ❌ weekly review 锚点更新（SKILLS_SPEC §8 step 6）—— v0.2 引入 review 技能
- ❌ 主动提醒（memory 事件）—— v0.3

---

## 3. 输入

| 参数 | 必填 | 默认 | 说明 |
|------|------|------|------|
| `content` | 否 | 空 | 用户口述，可为一句话或多段；为空时 AI 引导 |
| `date` | 否 | 今天 | 指定日期 `YYYY-MM-DD`，支持补写昨天/前天 |
| `append` | 否 | `true` | 文件已存在时追加而非覆盖 |

---

## 4. 工作流

### 步骤 1 · 加载或创建日志文件

- **新建路径**：`05_outputs/daily/YYYY/MM/YYYY-MM-DD-<summary>.md`
  - `<summary>` 由 LLM 从用户当日 content 提炼 2-5 个词 kebab-case（限 30 字符），如 `rag-eval-debug` / `launch-prep` / `interview-cycle`
  - 内容空 / 不可提炼（如纯「记一下今天」）→ 退为纯日期 `YYYY-MM-DD.md`
- **旧文件优先**：同一天若已存在任何形式的文件（`YYYY-MM-DD.md` 或 `YYYY-MM-DD-*.md`）→ **加载既有文件编辑，不重新提炼 summary，不创建新文件**（文件名稳定性硬约束，避免 wikilink 断）
- 月份子目录不存在 → 创建（含 `.gitkeep`）
- 文件不存在 → 基于 [`templates/zh/daily.md`](../../templates/zh/daily.md) 创建
- 文件已存在 → 加载现有内容；`append=true` 时追加，`false` 时提示是否覆盖（默认不覆盖）

### 步骤 2 · 解析用户输入

将 `content` 按以下规则拆分到 4 段：

| 段 | 启发式 |
|----|--------|
| **做了什么** | 包含动词 + 具体对象（开会/编码/沟通/评审/写文档） |
| **学到什么** | 含"学到/意识到/发现/明白了"等元认知关键词，或与已有 concept 笔记相关 |
| **想法** | 含"觉得/想象/如果/可能/或许"等推测语气 |
| **卡点** | 含"卡住/阻塞/不知道/搞不定/失败"等负面或阻碍词 |

模糊无法归类的句子 → 默认放入「做了什么」，由反问环节纠正。

### 步骤 3 · 反问补充（关键特性 · 最多 2 轮）

#### 触发反问的条件

某段描述**笼统或缺失**时触发，典型场景：

| 笼统输入 | 反问示例 |
|---------|---------|
| 「开会」 | 「这个会议主题是什么？有没有决策需要记录？」 |
| 「学了很多」 | 「你说『学了很多』，能具体列出 1-2 个要点吗？」 |
| 「搞 X」 | 「X 的具体内容是？结果如何？」 |
| 4 段全空 | 「今天最有印象的一件事是？」 |

#### 反问规则

- **每轮最多 1-2 个问题**（避免问卷感）
- **总共最多 2 轮**（避免疲劳）
- 用户拒绝或说「就这样」→ 立即停止，接受当前输入
- 反问记录写入文件底部 callout（见 `templates/zh/daily.md` 反问记录区）

### 步骤 3.5 · AI 润色提议（v1.2+ · 关键特性）

**与反问机制的互补关系**：
- 反问（步骤 3）：让用户**自己补全** vague input（被动）
- 润色（步骤 3.5）：AI **主动扩写**短句（主动）
- 串联顺序：先反问补全明显缺失 → 再润色提议优化表达

#### 扫描候选

反问结束后，扫描 4 段（做了什么 / 学到什么 / 想法 / 卡点）中所有列表项，识别**短句候选**：

- 字符数 < 30（默认阈值，可被 `kb.config.capture_ai.polish_threshold_chars` 覆盖）
- 或无标点（。！？.!?）
- 或含「开会」「修 bug」「学了很多」「搞 X」等典型 vague 模式

**反例**：长描述（> 30 字符、含完整上下文）→ 不进润色菜单。

#### 一次性呈现编号菜单

对所有候选短句同时生成润色版，一次性向用户呈现（避免逐条询问造成疲劳）：

```
✨ 检测到以下条目可能过于简短，是否润色？

做了什么 段：
  ① 「修 bug」     → 「修复用户登录时 token 过期未自动刷新的 bug」
  ② 「开会」       → 「参加 RAG 模块评审会，决策向量库选型（Milvus vs pgvector）」
学到什么 段：
  ③ 「学了很多」   → 「学了 defuddle 抓取机制、Obsidian Bases 视图配置」

[1] 全部润色   [2] 选编号润色（如 ①③）   [3] 全部保留   [4] 单条再改（输入编号）
```

#### 用户响应处理

- **[1] 全部润色**：所有候选条目替换为润色版
- **[2] 选编号润色**：仅替换指定条目
- **[3] 全部保留**：跳过润色，走原流程
- **[4] 单条再改**：用户输编号 + 补充要求，重新生成（上限 `polish_max_rounds` 默认 3 轮/条）

#### 原句保存机制（与 capture 区别）

daily 是日志性文件，**不**单独存 `source.original_text`，而是用**行内 HTML 注释**保留原句：

```markdown
## 做了什么
- 修复用户登录时 token 过期未自动刷新的 bug
  <!-- original: 修 bug -->
- 参加 RAG 模块评审会，决策向量库选型（Milvus vs pgvector）
  <!-- original: 开会 -->
```

frontmatter 加 `ai_polished_entries: [1, 2]`（被润色条目的编号列表，从 1 开始计数，跨段连续编号）。

#### 降级

- LLM 不可用 → 跳过润色提议，走原流程
- 用户长时间未选 → 默认 [3] 全部保留（不阻塞日志写入）
- 单条润色版与原句相似度 > 0.9 → 该条自动跳过

### 步骤 4 · wikilinks 自动抽取

1. 扫描库内已有笔记标题（v0.1 范围：`02_areas/`、`01_resources/`、`04_projects/`、`03_goals/`、`05_outputs/decisions/`、`05_outputs/daily/`）。
2. 用户文本中出现某标题（或强别名）→ 自动转 `[[标题]]`。
3. **幂等**：已是 `[[...]]` 的不重复转换。
4. 标题冲突（多个同名笔记）→ 选最近 updated 的一条，加脚注。

### 步骤 5 · 待入库项检测

识别文本中的「值得记」信号：

- 用户说「这个想法值得记」「这个要入库」「先存着」
- AI 判断某句话信息密度高且与已有笔记主题相关（但不直接重复）
- 某个学到点有 concept 化潜力

提示：

```markdown
## 待入库

> AI 检测到以下内容值得单独入库：

- [ ] {{候选想法 1 · 简述}}
- [ ] {{候选想法 2}}

是否现在调用 `quick-kb-capture`？
```

**非阻塞** —— 用户可忽略；列表写入文件供后续手动处理。

### 步骤 6 · 写入文件

- frontmatter（基于 v0.1 子集）：

  ```yaml
  ---
  title: 2026-08-09 日志
  type: daily
  created: 2026-08-09
  updated: 2026-08-09
  tags:
    - daily
  status: active
  ---
  ```

  > daily 笔记通常无 `domain`/`source`/`confidence`，可留空不写。

- 正文：4 段 + 待入库 + 反问记录 callout
- `append=true` 时新内容追加在对应段落下（用 `- ` 列表追加），不覆盖既有行
- 更新 `updated` 为今天

### 步骤 7 · 反馈输出

```
✓ 日志已更新：05_outputs/daily/2026/08/2026-08-09.md
  追加：做了什么 ×N / 学到什么 ×N / 想法 ×N / 卡点 ×N
  wikilinks：[[项目 X]]、[[某 concept]]
  待入库候选：N 条（见文件末尾「待入库」段）

  → quick-kb-capture 把候选入库
  → 明天继续：quick-kb-daily
```

> 💡 **下一步**：将检测到的待入库项运行 `quick-kb-capture` 采集，把日志中的候选想法正式落盘。

## 5. 输出契约

### 5.1 路径

`05_outputs/daily/YYYY/MM/YYYY-MM-DD-<summary>.md`（新建；summary 由 LLM 从内容提炼 2-5 词 kebab-case；同日已存在旧文件则编辑不改名；详见 §步骤 1）

### 5.2 frontmatter

严格遵循 [`references/frontmatter-v0.1.md`](../../references/frontmatter-v0.1.md)：

- 必填：`title` / `type=daily` / `created` / `updated` / `tags=[daily]` / `status`
- 可选：`domain`（通常无）
- v1.2+ 可选扩展：`ai_polished_entries: [编号列表]`（仅当步骤 3.5 有条目被润色时才写）

### 5.3 正文结构

固定 4 段 + 待入库段：

```markdown
# YYYY-MM-DD

## 做了什么
- ...

## 学到什么
- ...

## 想法
- ...

## 卡点
- ...

## 待入库
- [ ] ...

<!-- 反问记录 -->
```

---

## 6. 边界

- **反问有上限** —— 最多 2 轮，用户拒绝立即停。
- **不强制结构** —— 用户一句话也能记录，反问是增强不是阻塞。
- **默认不改正文语义** —— 只做拆段、wikilink 转换、追加，**不改写用户原话**；**例外**：v1.2+ 步骤 3.5 中用户显式选「润色」的短句，用润色版替换，原句以 `<!-- original: ... -->` 行内 HTML 注释保留。
- **润色不批量改写整段** —— 仅针对识别出的单条短句，逐条提议；整段长描述不进润色流程。
- **不更新 weekly review 锚点** —— v0.2 引入 review 技能后联动。
- **不写 v0.2+ 字段** —— frontmatter 严格用 v0.1 子集（`ai_polished_entries` 是 v1.2+ 可选扩展，不算 v0.2 正式字段）。

## 7. 降级路径

| 场景 | 降级行为 |
|------|---------|
| 用户输入为空且拒绝反问 | 创建空骨架日志（4 段全 `{{}}`），标 `status: draft` |
| 输入太短无法拆段 | 全部放「做了什么」，提示「明天可补充更多细节」 |
| 库内无任何笔记（首次使用） | 跳过 wikilinks 抽取，待入库检测跳过 |
| 同名 daily 文件已存在 | `append=true`（默认）追加；`append=false` 时询问是否覆盖 |
| 笔记标题冲突 | 选最近 updated 的，加脚注 `[1]` 说明 |
| LLM 不可用（v1.2+ 润色） | 跳过润色提议，走原流程 |
| 用户未响应润色菜单（v1.2+） | 默认全部保留，不阻塞日志写入 |

## 8. 反问 Prompt（参考）

```
你是 quick-knowledge 的 daily 助手。任务：

1. 用户给了今天的一段日志描述。
2. 拆分为四段：做了什么 / 学到什么 / 想法 / 卡点（无法判断的归「做了什么」）。
3. 评估每段是否「过于笼统」（特征：动词无对象、形容词无名词、抽象无具体）。
4. 若存在笼统段，提出 1-2 个具体问题（每轮 ≤2 问，最多 2 轮）。
5. 若用户拒绝回答或说「就这样」，立即停止，输出当前结构化结果。
6. 严禁变成问卷 —— 反问是增强，不是阻塞。

输出 JSON：
{
  "sections": {
    "did": ["..."],
    "learned": ["..."],
    "ideas": ["..."],
    "blockers": ["..."]
  },
  "needs_followup": true|false,
  "followup_questions": ["...", "..."],   // ≤2 条；needs_followup=false 时为空
  "capture_candidates": ["..."]            // 待入库候选
}
```

## 9. 幂等保证

- **同一天再次调用**：默认追加，不覆盖既有内容
- **用户明确 `append=false` + 同意覆盖**：才覆盖；否则永远追加
- **wikilinks 转换**：已是 `[[...]]` 的不重复处理
