# quick-kb-daily

> 每日日志入口。**反问是增强不是阻塞** —— 用户只说一句话也能记录。

---

## 0. 顶层不变量（覆盖一切，违反即错误）

**summary 提炼是硬约束** —— 新建日志文件时，**必须**按 [`filename-summary-rules.md`](../../references/filename-summary-rules.md) §2 机械判定：Step 1「强制纯日期清单」未命中 → 文件名**必须**含 `<YYYY-MM-DD>-<summary>.md` 段。**严禁**用以下语义借口退化为纯日期（`YYYY-MM-DD.md`）：

- 「内容笼统 / 表达 vague / 不够具体」
- 「主题分散 / 跨多个领域 / 难以归纳」
- 「会议型日志 / 学习型日志无可提炼主题」
- 「信息不足 / 用户表达模糊」

**任何"内容笼统所以退化为纯日期"的行为都是错误**。笼统恰恰是用户原始表达——summary 反映原始表达即可（如「开了一天的会」→ `meeting-day`，**不允**许以「会议笼统」为由退化纯日期）。「内容真的为空」通过机械判定（4 段全空 / 实质字符 < 5 / 仅元描述），**绝不**作为语义借口。

---

## 1. 何时调用

- 用户说「今天的日志」「记日志」「daily」「今天做了什么」
- 一天结束前回顾时
- 接续前一天的日志

## 2. v0.1 范围

### 做

- 加载/创建 `05_outputs/daily/YYYY/MM/YYYY-MM-DD-<summary>.md`（新建带 summary；同日已有旧文件 → 编辑不改名，详见 §步骤 1）
- 4 段拆分：做了什么 / 学到什么 / 想法 / 卡点
- **反问机制**（最多 2 轮，不变成问卷）
- wikilinks 自动抽取（识别已有笔记标题）
- 待入库项提示（建议调用 quick-kb-capture）
- frontmatter 用 v0.1 子集

### 不做

- ❌ weekly review 锚点更新（SKILLS_SPEC §8 step 6）—— v0.2 引入 review 技能
- ❌ 主动提醒（memory 事件）—— v0.3

## 3. 输入

| 参数 | 必填 | 默认 | 说明 |
|------|------|------|------|
| `content` | 否 | 空 | 用户口述，可为一句话或多段；为空时 AI 引导 |
| `date` | 否 | 今天 | 指定日期 `YYYY-MM-DD`，支持补写昨天/前天 |
| `append` | 否 | `true` | 文件已存在时追加而非覆盖 |
| `polish_mode` | 否 | `confirm` | 润色模式：`confirm`（编号菜单，默认）/ `auto`（全部润色）/ `skip`（不润色）。覆盖 `kb.config.yaml` 中 `polish.default_mode` 配置 |

## 4. 工作流

### 步骤 1 · 加载或创建日志文件

**summary 提炼判定**严格按 [`filename-summary-rules.md`](../../references/filename-summary-rules.md) §2 决策表逐步走（不许用单一语义条件宽放）：

**Step 1 · 先查「强制纯日期」清单**（命中任一即纯日期 `YYYY-MM-DD.md`，禁止提炼）：

| # | 强制纯日期条件 | 判定 |
|---|--------------|------|
| 1 | content 完全为空 | null / 空字符串 / 仅空白 |
| 2 | 4 段解析后全部为空 | did / learned / ideas / blockers 均无条目 |
| 3 | 实质字符数 < 5 | 去掉元描述后剩 < 5 字符（「ok」/「没事」/「休息」/「-」） |
| 4 | 仅含纯元描述且无事件关键词 | 字面是「今天没什么」/「就这些」/「完毕」/「没特别要记」/「日常」之一且无具体名词 |

**Step 2 · 未命中 → 必须提炼 summary**：从最有实质内容的段落抽 2-5 词 ASCII kebab-case（限 30 字符）。

> **禁止语义绕过（硬约束）**：上述是机械字符判定。即使输入字面是「开了一天的会」「学了很多」「没什么特别的」「日常开发」等笼统表达，**仍按 Step 2 提炼 summary**（如 `meeting-day` / `mcp-learning` / `routine-dev` / `daily-grind`）。**严禁**用「内容笼统 / 主题分散 / 会议型日志不可提炼」等语义理由退化纯日期。

**错误绕过反例**（模型常见的偷懒模式，必须避免）：

| 输入 | 错误行为 | 正确行为 |
|------|---------|---------|
| 「今天搞了一下午 RAG 调参」 | ❌ `2026-08-13.md`（借口「调参笼统」） | ✅ `2026-08-13-rag-tuning.md` |
| 「写了几行代码，修了个登录 bug」 | ❌ 纯日期（借口「bug 不具体」） | ✅ `2026-08-13-login-bugfix.md` |
| 「开了一天的会，重点是 RAG 评审」 | ❌ 纯日期（借口「会议笼统」） | ✅ `2026-08-13-rag-review-meetings.md` 或 `meeting-day.md` |
| 「学了很多关于 mcp 的东西」 | ❌ 纯日期（借口「学了很多不具体」） | ✅ `2026-08-13-mcp-learning.md` |
| 「没什么特别的，就是日常开发」 | ❌ 纯日期（借口「日常太笼统」） | ✅ `2026-08-13-routine-dev.md` |
| 「」/「ok」/「没事」 | ✓ 纯日期（Step 1 #3 命中） | ✅ `2026-08-13.md`（纯日期正确） |

**加载/创建逻辑**：

- **新建路径**：`05_outputs/daily/YYYY/MM/YYYY-MM-DD-<summary>.md`（summary 由 Step 2 提炼，如 `rag-eval-debug` / `launch-prep` / `interview-cycle` / `meeting-day` / `routine-dev`）
- **旧文件优先**：同一天若已存在任何形式的文件（`YYYY-MM-DD.md` 或 `YYYY-MM-DD-*.md`）→ **加载既有文件编辑，不重新提炼 summary，不创建新文件**（文件名稳定性硬约束，避免 wikilink 断）
- 月份子目录不存在 → 创建（含 `.gitkeep`）
- 文件不存在 → 基于 vault `99_system/templates/{lang}/daily.md`（由 init 铺设；v1.5 WP1 统一表述；仓库源 `templates/zh/daily.md`）创建
- 文件已存在 → 加载现有内容；`append=true` 时追加，`false` 时提示是否覆盖（默认不覆盖）

### 步骤 2 · 解析用户输入

将 `content` 按以下规则拆分到 4 段：

| 段 | 启发式 |
|----|--------|
| **做了什么** | 包含动词 + 具体对象（开会/编码/沟通/评审/写文档） |
| **学到什么** | 含"学到/意识到/发现/明白了"等元认知关键词，或与已有 concept 笔记相关 |
| **想法** | 含"觉得/想象/如果/可能/或许"等推测语气 |
| **卡点** | 含"卡住/阻塞/不知道/搞不定/失败"等负面或阻碍词 |

模糊无法归类的句子 → 默认放入「做了什么」，由反问环节纠正。

### 步骤 3 · 反问补充（关键特性 · 最多 2 轮）

#### 触发反问的条件

某段描述**笼统或缺失**时触发，典型场景：

| 笼统输入 | 反问示例 |
|---------|---------|
| 「开会」 | 「这个会议主题是什么？有没有决策需要记录？」 |
| 「学了很多」 | 「你说『学了很多』，能具体列出 1-2 个要点吗？」 |
| 「搞 X」 | 「X 的具体内容是？结果如何？」 |
| 4 段全空 | 「今天最有印象的一件事是？」 |

#### 反问规则

- **每轮最多 1-2 个问题**（避免问卷感）
- **总共最多 2 轮**（避免疲劳）
- 用户拒绝或说「就这样」→ 立即停止，接受当前输入
- 反问记录写入文件底部 callout（见 `templates/zh/daily.md` 反问记录区）

### 步骤 3.5 · AI 润色提议（v1.2+ · 关键特性）

**与反问机制的互补关系**：
- 反问（步骤 3）：让用户**自己补全** vague input（被动）
- 润色（步骤 3.5）：AI **主动扩写**短句（主动）
- 串联顺序：先反问补全明显缺失 → 再润色提议优化表达

#### 扫描候选

反问结束后，扫描 4 段（做了什么 / 学到什么 / 想法 / 卡点）中所有列表项，识别**短句候选**：

- 字符数 < 30（默认阈值，可被 `kb.config.capture_ai.polish_threshold_chars` 覆盖）
- 或无标点（。！？.!?）
- 或含「开会」「修 bug」「学了很多」「搞 X」等典型 vague 模式

**反例**：长描述（> 30 字符、含完整上下文）→ 不进润色菜单。

#### 一次性呈现编号菜单

对所有候选短句同时生成润色版，一次性向用户呈现（避免逐条询问造成疲劳）：

```
✨ 检测到以下条目可能过于简短，是否润色？

做了什么 段：
  ① 「修 bug」     → 「修复用户登录时 token 过期未自动刷新的 bug」
  ② 「开会」       → 「参加 RAG 模块评审会，决策向量库选型（Milvus vs pgvector）」
学到什么 段：
  ③ 「学了很多」   → 「学了 defuddle 抓取机制、Obsidian Bases 视图配置」

[1] 全部润色   [2] 选编号润色（如 ①③）   [3] 全部保留   [4] 单条再改（输入编号）
```

#### 用户响应处理

**判定 `polish_mode` 参数**（v1.7+）：
- **`polish_mode=skip`**：跳过润色流程，直接走原流程
- **`polish_mode=auto`**：跳过编号菜单，全部候选条目自动润色
- **`polish_mode=confirm`**（默认）：执行原编号菜单流程

**confirm 模式流程**（默认）：

- **[1] 全部润色**：所有候选条目替换为润色版
- **[2] 选编号润色**：仅替换指定条目
- **[3] 全部保留**：跳过润色，走原流程
- **[4] 单条再改**：用户输编号 + 补充要求，重新生成（上限 `polish_max_rounds` 默认 3 轮/条）

**auto 模式流程**（v1.7+）：

1. 对所有候选短句生成润色版
2. 跳过编号菜单，自动全部润色
3. 输出时注明「✓ 自动润色 N 条（polish_mode=auto）」

#### 原句保存机制（与 capture 区别）

daily 是日志性文件，**不**单独存 `source.original_text`，而是用**行内 HTML 注释**保留原句：

```markdown
## 做了什么
- 修复用户登录时 token 过期未自动刷新的 bug
  <!-- original: 修 bug -->
- 参加 RAG 模块评审会，决策向量库选型（Milvus vs pgvector）
  <!-- original: 开会 -->
```

frontmatter 加 `ai_polished_entries: [1, 2]`（被润色条目的编号列表，从 1 开始计数，跨段连续编号）。

#### 降级

- LLM 不可用 → 跳过润色提议，走原流程
- `polish_mode=auto` 时润色失败 → 跳过该条，保留原句
- 用户长时间未选（confirm 模式） → 默认 [3] 全部保留（不阻塞日志写入）
- 单条润色版与原句相似度 > 0.9 → 该条自动跳过

### 步骤 4 · wikilinks 自动抽取

**算法（v1.5 WP7 · v1.7 WP4-B 硬化）**：

1. **候选集构造**：扫描以下目录下所有 `.md` 文件的 basename（去扩展名）：
   - `02_areas/**`（含嵌套 domain 子树）
   - `07_principles/**`
   - `03_goals/**`
   - `04_projects/**`（不含 `_template/`）
   - `06_wiki/mocs/**`（v1.9.0 · MOC 标题可被日志引用）

2. **匹配规则（v1.7 WP4-B 硬化）**：
   - **仅匹配库内已存在笔记**：basename 必须完全匹配，禁止模糊匹配
   - **整词匹配 · 不区分大小写**：候选名作为独立词出现在文本中（前后是空格 / 标点 / 行首行尾）
   - **强别名匹配**：frontmatter `aliases` 字段内的别名等同 basename 处理
   - **标题长度阈值**：笔记标题长度 ≤ 3 字符时跳过（避免 `[[RAG]]`、`[[AI]]` 等误匹配）
   - **同一日志内去重**：同一 wikilink 在同一日志内仅生成一次（后续出现不再转换）
   - **用户已手写 [[]] 不重复**：若用户正文已手写 `[[...]]`，不重复生成

3. **幂等**：已是 `[[...]]` 的不重复转换

4. **冲突处理**：多个同名笔记 → 选最近 `updated` 的一条，加脚注 `[^n]` 注明其他同名笔记路径

5. **未命中但有高潜力名词**（v1.5 WP7 · 信息密度高但无对应笔记）：
   - 候选：名词长度 ≥ 3 字符 AND 在 4 段中重复出现 ≥ 2 次 AND 不在候选集内
   - 不自动建 wikilink（避免误链）
   - 列入「待入库」段（见 §步骤 5）

### 步骤 5 · 待入库项检测

识别文本中的「值得记」信号：

- 用户说「这个想法值得记」「这个要入库」「先存着」
- AI 判断某句话信息密度高且与已有笔记主题相关（但不直接重复）
- 某个学到点有 concept 化潜力

提示（v1.5 WP7 · 含一键命令，不自动触发）：

```markdown
## 待入库

> AI 检测到以下内容值得单独入库：

- [ ] {{候选想法 1 · 简述}}
      → 运行：`quick-kb-capture "{{候选想法 1 摘要}}"`
- [ ] {{候选想法 2}}
      → 运行：`quick-kb-capture "{{候选想法 2 摘要}}"`

💡 复制对应命令执行采集；daily 不自动触发 ingest（需用户确认）。
```

**非阻塞** —— 用户可忽略；列表写入文件供后续手动处理。

### 步骤 5.5 · 写入前校验（v1.8 WP2）

落盘前按 [`write-validation-rules.md`](../../references/write-validation-rules.md) 校验，任一失败 → 按规则修正后才写入，不得静默落盘不合规内容；无文件索引可查时在输出中 ⚠ 标注：

- **正文 wikilink 目标存在性**：所有 `[[X]]` 目标必须已存在于 vault 文件名索引（对照步骤 4 候选集）；无对应笔记文件的**术语性链接（如 `[[RAG]]`）禁止**，降级为普通文本或加粗
- frontmatter 必填字段齐全（`title` / `type=daily` / `created` / `updated` / `tags` / `status`，v0.1 子集）

### 步骤 6 · 写入文件

- frontmatter（基于 v0.1 子集）：

  ```yaml
  ---
  title: 2026-08-09 日志
  type: daily
  created: 2026-08-09
  updated: 2026-08-09
  tags:
    - daily
  status: active
  ---
  ```

  > daily 笔记通常无 `domain`/`source`/`confidence`，可留空不写。

- 正文：4 段 + 待入库 + 反问记录 callout
- `append=true` 时新内容追加在对应段落下（用 `- ` 列表追加），不覆盖既有行
- 更新 `updated` 为今天

### 步骤 7 · 反馈输出

```
✓ 日志已更新：05_outputs/daily/2026/08/2026-08-09-rag-eval-debug.md
  追加：做了什么 ×N / 学到什么 ×N / 想法 ×N / 卡点 ×N
  wikilinks：[[项目 X]]、[[某 concept]]
  待入库候选：N 条（见文件末尾「待入库」段）

  → quick-kb-capture 把候选入库
  → 明天继续：quick-kb-daily
```

## 5. 输出契约

### 5.1 路径

`05_outputs/daily/YYYY/MM/YYYY-MM-DD-<summary>.md`（新建；summary 由 LLM 从内容提炼 2-5 词 kebab-case；同日已存在旧文件则编辑不改名；详见 §步骤 1）

### 5.2 frontmatter

严格遵循 [`references/frontmatter-v0.1.md`](../../references/frontmatter-v0.1.md)：

- 必填：`title` / `type=daily` / `created` / `updated` / `tags=[daily]` / `status`
- 可选：`domain`（通常无）
- v1.2+ 可选扩展：`ai_polished_entries: [编号列表]`（仅当步骤 3.5 有条目被润色时才写）

### 5.3 正文结构

固定 4 段 + 待入库段：

```markdown
# YYYY-MM-DD

## 做了什么
- ...

## 学到什么
- ...

## 想法
- ...

## 卡点
- ...

## 待入库
- [ ] ...

<!-- 反问记录 -->
```

## 6. 边界

- **反问有上限** —— 最多 2 轮，用户拒绝立即停。
- **不强制结构** —— 用户一句话也能记录，反问是增强不是阻塞。
- **默认不改正文语义** —— 只做拆段、wikilink 转换、追加，**不改写用户原话**；**例外**：v1.2+ 步骤 3.5 中用户显式选「润色」的短句，用润色版替换，原句以 `<!-- original: ... -->` 行内 HTML 注释保留。
- **润色不批量改写整段** —— 仅针对识别出的单条短句，逐条提议；整段长描述不进润色流程。
- **不更新 weekly review 锚点** —— v0.2 引入 review 技能后联动。
- **不写 v0.2+ 字段** —— frontmatter 严格用 v0.1 子集（`ai_polished_entries` 是 v1.2+ 可选扩展，不算 v0.2 正式字段）。

## 7. 降级路径

| 场景 | 降级行为 |
|------|---------|
| 用户输入为空且拒绝反问 | 创建空骨架日志（4 段全 `{{}}`），标 `status: draft` |
| 输入太短无法拆段 | 全部放「做了什么」，提示「明天可补充更多细节」 |
| 库内无任何笔记（首次使用） | 跳过 wikilinks 抽取，待入库检测跳过 |
| 同名 daily 文件已存在 | `append=true`（默认）追加；`append=false` 时询问是否覆盖 |
| 笔记标题冲突 | 选最近 updated 的，加脚注 `[1]` 说明 |
| LLM 不可用（v1.2+ 润色） | 跳过润色提议，走原流程 |
| 用户未响应润色菜单（v1.2+） | 默认全部保留，不阻塞日志写入 |

## 8. 反问 Prompt（参考）

```
你是 quick-knowledge 的 daily 助手。任务：

1. 用户给了今天的一段日志描述。
2. 拆分为四段：做了什么 / 学到什么 / 想法 / 卡点（无法判断的归「做了什么」）。
3. 评估每段是否「过于笼统」（特征：动词无对象、形容词无名词、抽象无具体）。
4. 若存在笼统段，提出 1-2 个具体问题（每轮 ≤2 问，最多 2 轮）。
5. 若用户拒绝回答或说「就这样」，立即停止，输出当前结构化结果。
6. 严禁变成问卷 —— 反问是增强，不是阻塞。

输出 JSON：
{
  "sections": {
    "did": ["..."],
    "learned": ["..."],
    "ideas": ["..."],
    "blockers": ["..."]
  },
  "needs_followup": true|false,
  "followup_questions": ["...", "..."],   // ≤2 条；needs_followup=false 时为空
  "capture_candidates": ["..."]            // 待入库候选
}
```

## 9. 幂等保证

- **同一天再次调用**：默认追加，不覆盖既有内容
- **用户明确 `append=false` + 同意覆盖**：才覆盖；否则永远追加
- **wikilinks 转换**：已是 `[[...]]` 的不重复处理
