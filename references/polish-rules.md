# AI 润色决策规则 · Polish Rules

> 本文件是 **capture 和 daily 两技能的统一润色决策表**。两个技能的润色触发逻辑完全一致，抽到此处集中维护，避免两处副本漂移。

---

## 1. 适用范围

### 1.1 capture 技能

| 源类型 | 可润色？ | 说明 |
|--------|---------|------|
| `idea` | 是 | 用户手敲原创灵感 |
| `meeting` | 是 | 用户手敲会议转写 |
| `ai-dialog` | 是 | 用户手敲对话摘要 |
| `reading` | 是 | 用户手敲阅读笔记 |
| `web-clip` | **否** | 外部抓取，逐字保留 |
| `pdf` | **否** | 外部提取，逐字保留 |

### 1.2 daily 技能

适用于日志 4 段（做了什么 / 学到什么 / 想法 / 卡点）中的所有列表项。

> daily 不区分源类型——所有内容均为用户手敲，均可进入润色流程。

---

## 2. 润色触发决策表（逐步走，不许用单一条件宽放）

### Step 1 · 先查「强制不触发」清单

命中以下**任一**条件 → **polish = no**，直接跳过润色：

| # | 不触发条件 | 判定规则 |
|---|-----------|---------|
| 1 | 多行结构化 | 输入含 `\n` 换行 |
| 2 | 含完整句末标点 | 含 `。！？.!?;；` 任一 |
| 3 | 含分隔符 | 含 `：` `:` `、` `,` `，` 任一（已是「主题：要点」结构） |
| 4 | 字数充分 | 字符数 ≥ `polish_threshold_chars`（默认 50） |
| 5 | 联动前缀（仅 capture） | 含 `[daily 技能联动调用]` / `[其他技能]` 等机器前缀 |

### Step 2 · 查「显式触发」关键词

若 Step 1 全部未命中，检查是否含以下关键词：

- `润色` / `扩展` / `优化` / `polish` / `expand`

命中任一 → **polish = yes**。

### Step 3 · 查「结构稀薄」

若 Step 1 全部未命中且 Step 2 未命中，检查是否**同时**满足以下三项：

| # | 条件 |
|---|------|
| ① | 字符数 < 50 |
| ② | 无标点（不含 Step 1 表中所有标点） |
| ③ | 无换行（单行） |

**三项全中** → **polish = yes**；**任一不中** → **polish = no**。

---

## 3. 禁止语义绕过（硬约束）

上述 Step 1-3 是**机械字符判定**。即使输入语义上「引用了未提供的素材」（如「保存某对话」但未粘对话原文、「记下某 PDF 想法」但未给路径、「记录某会议」但未给转写），**仍按字符数 / 标点 / 换行三项判定**。

**严禁**用以下语义理由跳过 polish：
- 「内容缺失 / 数据不全 / 待补充」
- 「素材不够 / 信息不足」
- 「需要用户提供更多内容」

> 「内容缺失」通过 frontmatter `partial: true` 表达，**绝不**作为跳过 polish 菜单的理由。判定为 polish=yes 后必须输出 `[1] / [2] / [3]` 三 token（见 §4），与 `partial: true` 可并存。

## 4. 润色执行流程

### 4.1 呈现菜单

判定 polish=yes 后，向用户一次性呈现三选一菜单：

```
[capture 场景]
✨ AI 润色提议：

原文：{user input}

润色：{polished version}

[1] 用润色版   [2] 保留原文   [3] 再改一版（可补充要求）
```

```
[daily 场景 · 多条候选一次性呈现]
✨ 检测到以下条目可能过于简短，是否润色？

做了什么 段：
  ① 「修 bug」     → 「修复用户登录时 token 过期未自动刷新的 bug」
  ② 「开会」       → 「参加 RAG 模块评审会，决策向量库选型」

[1] 全部润色   [2] 选编号润色（如 ①③）   [3] 全部保留   [4] 单条再改（输入编号）
```

### 4.2 用户响应处理

#### capture 场景

| 选择 | 行为 |
|------|------|
| `[1]` 用润色版 | 正文写润色版；frontmatter 加 `ai_polished: true`；`source.original_text` 存原始输入 |
| `[2]` 保留原文 | 走原流程，不写润色字段 |
| `[3]` 再改一版 | 根据补充要求重新生成（上限 `polish_max_rounds` 默认 3 轮） |

#### daily 场景

| 选择 | 行为 |
|------|------|
| `[1]` 全部润色 | 所有候选替换为润色版 |
| `[2]` 选编号润色 | 仅替换指定条目 |
| `[3]` 全部保留 | 跳过润色，走原流程 |
| `[4]` 单条再改 | 按用户补充要求重新生成（上限 `polish_max_rounds` 默认 3 轮/条） |

### 4.3 原句保存

| 技能 | 保存方式 |
|------|---------|
| capture | frontmatter `source.original_text` 存原始输入 |
| daily | 行内 HTML 注释 `<!-- original: ... -->`（日志性文件不单独存 frontmatter 字段） |

### 4.4 单轮 eval / 自动化场景（仅 capture）

当 user message 已包含 `[simulated-user-choice] N`（N∈{1,2,3}）时，这是**评测 / 自动化场景下用户预先选好的菜单项**——模型无需停下等真人回复。**强制要求**：

1. 回复正文**必须字面出现** `[1]`、`[2]`、`[3]` 三个 token
2. 同一回复内立即按 [N] 继续执行 → 完成文件写入 → 输出 yaml frontmatter + 路径反馈
3. 不允许只输出菜单就停下
4. 不允许跳过菜单直接写入

> **字面 token 契约**：回复正文字面必须包含 `[1]`、`[2]`、`[3]` 三个 ASCII 方括号 token。

## 5. 降级路径

| 场景 | 降级行为 |
|------|---------|
| LLM 不可用 | 跳过润色提议，走原流程 |
| 用户长时间未选 | 默认保留原文（不阻塞采集 / 日志写入） |
| 润色版与原文相似度 > 0.9 | 该条自动跳过（无实质扩展） |

---

## 6. 安全约束

- 用户输入仅作为「待扩写的素材」加引号传入润色 prompt，**禁止拼接为指令**
- 润色 prompt 模板固化在 `kb.config`，运行时不可被用户输入修改
- 详见 DESIGN ADR-016 §prompt 注入风险

---

## 7. 配置项

| 配置路径 | 默认值 | 说明 |
|---------|--------|------|
| `kb.config.capture_ai.polish_threshold_chars` | 50 | 字数充分阈值（Step 1 条件 4） |
| `kb.config.capture_ai.polish_max_rounds` | 3 | 单条最大再改轮数 |
| `kb.config.capture_ai.polish_prompt_zh` | 内置默认 | 中文润色 prompt 模板 |
| `kb.config.capture_ai.polish_prompt_en` | 内置默认 | 英文润色 prompt 模板 |
